# 一、Agent Loop 完整走查（天气助手实战推演）

## 运行时全景图

```
┌────────────────────────────────────────────────────────────┐
│                     你的程序（Agent Runtime）                 │
│                                                            │
│  ① 组装消息       ② 调 API        ③ 看回复         ④ 执行工具   │
│  用户问题           给 LLM           LLM 说：       你的代码    │
│  历史记录 ────→  {messages} ──→  "我要调工具" ──→ 调用函数    │
│  工具定义             │               │               │      │
│                      │               │               │      │
│                     ┌▼───────────────▼─┐             ▼      │
│  ▲                  │      LLM 模型      │         返回结果   │
│  │                  │  (只输出文字, 不做  │         (JSON/文本) │
│  │                  │   任何真实动作)     │              │      │
│  │                  └─────────────────┘              │      │
│  └─────────── ⑤ 把工具结果追加进历史 ←────────────────┘      │
│                    └───────── 回到 ②（下一次循环）            │
└────────────────────────────────────────────────────────────┘
```

## 关键认知

> **LLM 是"只会说话的参谋"，你（Runtime）才是"动手的执行官"。**

LLM 每一轮都是"瞎子"——它不联网、不执行、什么都不做，
**只靠你喂给它的文字做判断**。工具结果和错误信息是它唯一的"眼睛"。

## 完整走一遍「北京天气助手」

### 第 1 轮
- 组装：`用户: "北京今天多少度?"` + 工具菜单 `[get_weather(city), calculate(a, b, op)]`
- LLM 回复的不是答案，而是结构化调用请求：
```json
{ "tool": "get_weather", "arguments": { "city": "北京" } }
```
- 你的代码执行 `get_weather("北京")` → `{ "temp": 25, "condition": "晴" }`
- 追加进历史：
```
用户: 北京今天多少度?
助手: [调用 get_weather(city=北京)]
工具: { "temp": 25, "condition": "晴" }
```

### 第 2 轮
- 整段历史再次发给 LLM
- LLM 看到工具已返回 25°C，信息足够 → 直接回答："北京今天 25°C，晴。"
- 程序检测到回复没有工具调用 → 循环结束 ✅

> **推论：** 任何 Agent 代码的核心就是"历史累积式发送"。
> 工具结果不进历史，循环就没有意义。

# 二、Agent 怎么纠错？（疑问① → 已解决 ✅）

**纠错不是魔法，是"报错也走同一条循环"。**

## 推演：查长沙天气但 API 报错

**第 1 轮**：调 `get_weather(city="长沙")`
**你的代码把报错当工具结果追加进历史：**
```
用户: 长沙冷不冷?
助手: [调用 get_weather(city=长沙)]
工具: ERROR: 免费套餐不支持"长沙"城市代码，code=404
```
**第 2 轮**：LLM 看到报错 → 合理的两种行为：
1. 换正确的城市代码重试（长沙 code = `101250101`）
2. 诚实承认"暂时查不到"

两种都是正确行为——**错误信息进入循环，模型就能基于它决策**。

## 为什么 Agent 能"自己改 bug"？

> Claude Code / Cursor 的"报错→自动修"本质：**把编译错误、测试输出当作工具结果喂回去**。
> 不是模型多聪明，而是循环转得够快、错误喂得够准。

Anthropic 说的"Agent 每一步都需要环境事实依据（ground truth）"：
工具返回值、报错、代码输出，都是 ground truth。没有它们，模型就是盲猜。

## 纠错的三道防线（串联）

| 防线 | 机制 | 白话 |
|------|------|------|
| 1. 错误回环 | 报错结果追加历史，模型看到再决策 | 让瞎子"摸到"错误 |
| 2. Ground Truth | 每步真实反馈验证上一步 | 只信执行结果，不猜 |
| 3. 护栏兜底 | 最大轮数 / 超时 / 无效重试 / 人工介入 | 防止循环烧钱发疯 |

# 三、多 Agent 怎么协作？（疑问② → 已解决 ✅）

**先立规矩：90% 的情况轮不到多 Agent。**
多 Agent = 成本×N + 错误传播×N。两个拆分信号：
1. 提示词要写满 if-else
2. 工具互相"长得像"导致选错（看相似度，不是看数量）

## 模式 A：管理者模式（Manager / Orchestrator）

```
                     ┌─────────────┐
                     │  总控 Agent   │ <── 唯一面对用户
                     │  (统一决策)    │
                     └──────┬──────┘
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │ 题目拆解   │    │ 查知识点  │    │ 查漏对照  │
    │ Agent    │    │ Agent    │    │ Agent    │
    └──────────┘    └──────────┘    └──────────┘
```
- 中央 Agent 把专家 Agent 当"工具"排队调用
- 适用：需要统一掌控、统一面对用户的场景（如教学助手）

## 模式 B：去中心化移交（Handoff / Decentralized）

```
  用户: "帮我看看数据结构作业有没有超范围"
      │
      ▼
┌──────────┐   超出知识范围? 是    ┌──────────┐
│  作业解析  │ ──────────────────→ │  算法专区  │
│  Agent   │                     │  Agent   │
└──────────┘                     └──────────┘
      │ 否(直接答)                  │ 全权处理, 不再回主流程
```
- 平级 Agent 之间直接交控制权，交出去就不管
- 适用：明确的分工、专家独立处理（如客服分诊 → 订单 Agent）

## 对照表

| 维度 | 管理者模式 | 去中心化移交 |
|------|-----------|-------------|
| 谁决策 | 中央统一掌控 | 各平级自己说了算 |
| 结构 | Central 调 Workers | Peer-to-Peer handoff |
| 适合 | 统一调度、面对一个用户 | 明确分工、专家独立 |
| 类比 | 项目经理 | 公司部门间转单 |

## 最关键的尺子（记住这条红线）

> 先加工具榨干单 Agent → 工具开始重叠再分组 → 才轮到多 Agent。
> 顺序永远不能反。
